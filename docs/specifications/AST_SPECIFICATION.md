## 1. Introduction

The NDL (Notch Document Language) AST is a strictly typed, model-independent tree representation of markdown-based documents within the Notch knowledge capture system. It serves as the canonical intermediate representation between raw markdown generation by AI models and final rendering in the Notch Reader.

The AST is produced by a deterministic parser (`src/document-system/parser/`) that converts standard markdown (supplemented by GFM alerts, Mermaid diagrams, KaTeX math, and semantic fenced blocks) into a typed node tree. This tree is then validated by a rule-based validator (`src/document-system/validator/`), enriched by a transformer pipeline (`src/document-system/transformers/`), and finally consumed by renderers and exporters (`src/document-system/renderer/`, `src/document-system/exporters/`).

### 1.1 Scope

- **In scope:** All document content nodes, hierarchical structure, metadata, validation contracts, serialization format, and renderer contracts.
- **Out of scope:** UI rendering implementation details, storage schemas, network protocols, editor state, and AI model internals.

### 1.2 Document Pipeline Context

```
Markdown (from AI model)
    |
    v
NDL Parser (marked lexer -> typed AST nodes)
    |
    v
NDL Validator (heading hierarchy, structure, content rules)
    |
    v
NDL Transformers (language normalization, ID generation, metadata enrichment)
    |
    v
Document Renderer (React components per node type)
    |
    v
Reader / PDF Export
```

## 2. Design Philosophy

### 2.1 Strictly Typed

Every node in the AST is represented by a dedicated TypeScript interface that extends `BaseNode`. The `type` property acts as a discriminated union discriminator, enabling exhaustive type narrowing in consumers. No node may exist without a known type. The union type `ASTNode` enumerates all permissible node types and is enforced at the parser boundary.

### 2.2 Model-Independent

The AST is agnostic to which AI model produced the originating markdown. All model-specific artifacts (formatting quirks, language aliases, structural inconsistencies) are normalized during parsing and transformation. The same markdown input, regardless of provenance, produces an identical AST. This ensures that the Reader's rendering path is decoupled from model choice.

### 2.3 Lossless Round-Trip

The parser preserves all source content: raw markdown text is retained in `ParagraphNode.raw`, original code block text is retained in `CodeNode.content`, and HTML-rendered equivalents are stored in `.html` fields where applicable. The exporter (`exportToMarkdown`) can reconstruct markdown from the AST with no semantic loss. This round-trip property is verified by the test suite.

### 2.4 Extensible via Union Types

New node types are added by:

1. Defining a new interface extending `BaseNode` with a unique `type` literal.
2. Adding the new type to the `ASTNode` discriminated union.
3. Implementing the required parser branch, validator rule, transformer handling, and renderer component.

No existing code requires modification beyond these four extension points. This union-based approach avoids inheritance hierarchies and permits feature-gated node types (e.g., `ApiNode`, `AccordionNode`) without polluting the core.

### 2.5 Position-Tracked

Every node carries an optional `SourcePosition` (`position?: SourcePosition`) recording its start and end line numbers in the original markdown. This enables precise error reporting, source mapping, and editor integration. The position field is populated by the parser and consumed by the validator for diagnostic messages.

### 2.6 Metadata-Extensible

Each node carries an optional `meta` record (`meta?: Record<string, unknown>`) for consumer-specific annotations without schema changes. This is used by transformers to store intermediate enrichment data (e.g., computed hash IDs, rendering hints) without altering the node's semantic interface.

## 3. Node Types

### 3.1 BaseNode (Abstract Base)

Every AST node extends this interface:

```
BaseNode {
  type: string           // Discriminator — unique literal per node type
  id?: string            // Stable identifier (auto-generated by transformer)
  position?: SourcePosition  // Source map (line range in original markdown)
  meta?: Record<string, unknown>  // Consumer-specific annotations
}
```

```
SourcePosition {
  startLine: number
  endLine: number
  startCol?: number
  endCol?: number
}
```

### 3.2 DocumentAST (Root Node)

The root container for a parsed or generated document. Not an `ASTNode` itself — it is the top-level structure returned by the parser and accepted by the validator.

```
DocumentAST {
  title: string                    // Document title (extracted from first H1)
  metadata: DocumentMetadata       // Computed metadata (word count, reading time, complexity)
  nodes: ASTNode[]                 // Flat ordered array of all content nodes
  hierarchy: ContentHierarchy      // Structured index (TOC, numbered figures/tables/diagrams/code)
  warnings: string[]               // Non-fatal parser warnings
}
```

```
DocumentMetadata {
  sourceUrl?: string               // Original source URL (if captured from web)
  sourceDomain?: string            // Extracted domain
  wordCount: number                // Total word count (whitespace-delimited)
  readingTimeMinutes: number       // Estimated reading time (wordCount / 220 WPM)
  documentClass?: string           // Inferred document type (research-paper, tutorial, news, general)
  capturedAt?: string              // ISO-8601 capture timestamp
  tags?: string[]                  // Extracted or user-supplied tags
  complexity?: number              // Computed complexity score (1-10)
  qualityScore?: number            // Computed quality score (1-10)
}
```

```
ContentHierarchy {
  toc: HeadingNode[]               // Nested heading tree (Table of Contents)
  figures: NumberedItem[]          // Figure reference index
  tables: NumberedItem[]           // Table reference index
  diagrams: NumberedItem[]         // Diagram reference index
  codeBlocks: NumberedItem[]       // Code block reference index
}
```

```
NumberedItem {
  type: 'figure' | 'table' | 'diagram' | 'code'
  number: number                   // Sequential number within document
  caption: string                  // Caption text (may be empty)
  sectionIndex: number             // Index of containing section
  id: string                       // Stable reference ID
}
```

### 3.3 HeadingNode

Represents a section heading.

```
HeadingNode extends BaseNode {
  type: 'heading'
  level: 1 | 2 | 3 | 4 | 5 | 6   // Heading depth (H1-H6)
  text: string                     // Plain text of the heading
  number?: string                  // Auto-assigned section number (e.g., "1.2.3")
  children: HeadingNode[]          // Nested child headings (hierarchy tree)
}
```

**Constraints:**

- `level` must be an integer between 1 and 6 inclusive.
- `children` may be empty; non-empty children form the TOC hierarchy.
- `number` is assigned by the parser's `assignNumbers()` pass; absent if numbering is disabled.
- The document must have exactly one H1 heading.

### 3.4 ParagraphNode

A block of prose content.

```
ParagraphNode extends BaseNode {
  type: 'paragraph'
  html: string                     // HTML-rendered content (links, bold, italic, code, math)
  raw: string                      // Original markdown source (for round-trip fidelity)
}
```

**Constraint:** At least one of `html` or `raw` must be non-empty.

### 3.5 ListNode

Ordered (numbered) or unordered (bulleted) list, optionally with task checkboxes.

```
ListItem {
  content: string                  // Text content of the item
  checked?: boolean                // Task state (present only for task lists)
  children?: ASTNode[]             // Nested child nodes (sub-lists, paragraphs)
}
```

```
ListNode extends BaseNode {
  type: 'list'
  ordered: boolean                 // true for ordered (numbered) lists
  items: ListItem[]                // List items
  start?: number                   // Starting number for ordered lists (defaults to 1)
}
```

**Constraints:**

- `items` must have at least one element.
- For task lists, `ordered` must be `false`.
- Nested lists are represented via `ListItem.children`, not recursive `ListNode` nesting.

### 3.6 CodeNode

A fenced code block with syntax metadata.

```
CodeLanguage =
  | 'typescript' | 'tsx' | 'javascript' | 'jsx'
  | 'python' | 'rust' | 'go' | 'ruby' | 'java'
  | 'kotlin' | 'swift' | 'c' | 'cpp' | 'csharp'
  | 'php' | 'html' | 'css' | 'scss' | 'sql'
  | 'json' | 'yaml' | 'toml' | 'xml' | 'markdown'
  | 'bash' | 'dockerfile' | 'graphql' | 'diff'
  | 'mermaid' | 'plantuml' | 'text'
```

```
CodeNode extends BaseNode {
  type: 'code'
  language: CodeLanguage           // Normalized language identifier
  content: string                  // Raw code content (preserved verbatim)
  filename?: string                // Optional source filename annotation
  highlightLines?: number[]        // Line numbers to highlight
  showLineNumbers: boolean         // Whether to render line number gutter
  diff?: boolean                   // Whether this is a diff block
}
```

**Constraints:**

- `language` must be one of the defined `CodeLanguage` literals (or a normalized alias). Unknown languages are normalized to `'text'`.
- Language aliases are normalized during transformation: `js -> javascript`, `ts -> typescript`, `py -> python`, `rb -> ruby`, `sh/shell/zsh -> bash`, `yml -> yaml`, `md -> markdown`, `kt -> kotlin`, `rs -> rust`, `cpp/c++/cxx -> cpp`, `cs/c# -> csharp`.
- Code blocks with `language` of `'mermaid'` or `'plantuml'` are promoted to `DiagramNode` during parsing.

### 3.7 DiagramNode

A typed diagram block renderable by an external engine.

```
DiagramKind =
  | 'flowchart' | 'sequenceDiagram' | 'classDiagram'
  | 'stateDiagram' | 'erDiagram' | 'journey'
  | 'gantt' | 'pie' | 'mindmap' | 'timeline'
  | 'gitGraph' | 'quadrantChart' | 'zenuml'
  | 'architecture' | 'plantuml'

DiagramEngine = 'mermaid' | 'plantuml' | 'ascii'
```

```
DiagramNode extends BaseNode {
  type: 'diagram'
  engine: DiagramEngine            // Rendering engine
  kind: DiagramKind                // Diagram type (flowchart, sequenceDiagram, etc.)
  content: string                  // Raw diagram source
  caption?: string                 // Optional caption text
  label?: string                   // Display label (e.g., "Diagram 1")
}
```

**Constraints:**

- `content` must be at least 3 non-whitespace characters and span at least 2 lines.
- `engine` is inferred from the code fence language: `mermaid` for mermaid-language blocks, `plantuml` for plantuml blocks.
- `kind` is inferred from the first line of content (e.g., `sequenceDiagram`, `flowchart LR`).

### 3.8 CalloutNode

An alert/admonition block with a semantic tone.

```
CalloutKind =
  | 'note' | 'tip' | 'warning' | 'danger' | 'info'
  | 'important' | 'caution' | 'success' | 'question'
```

```
CalloutNode extends BaseNode {
  type: 'callout'
  kind: CalloutKind                // Semantic tone
  title?: string                   // Optional title text
  html: string                     // HTML-rendered content body
}
```

**Constraints:**

- `kind` must be one of the 9 defined `CalloutKind` values.
- `html` may contain inline elements only (no block-level nesting).
- Detected via GFM alert syntax `[!KIND]` in blockquote tokens during parsing.
- Mermaid diagrams embedded within callout content are extracted and promoted to separate `DiagramNode` instances during transformer pass.

### 3.9 TableNode

A structured table with column definitions and rows.

```
ColumnDef {
  header: string                   // Header cell text
  align: 'left' | 'center' | 'right'  // Column alignment
}
```

```
TableNode extends BaseNode {
  type: 'table'
  columns: ColumnDef[]             // Column definitions
  rows: string[][]                 // Data rows (each row is an array of cell strings)
  caption?: string                 // Optional table caption
  sortable?: boolean               // Whether the table supports client-side sorting
}
```

**Constraints:**

- `columns` must have at least one entry.
- Every row in `rows` must have exactly `columns.length` cells.
- Row count may be zero (header-only table).

### 3.10 ImageNode

An embedded image with dimensions and caption.

```
ImageNode extends BaseNode {
  type: 'image'
  url: string                      // Absolute URL of the image
  alt: string                      // Alternative text (accessibility)
  caption?: string                 // Optional figure caption
  width?: number                   // Intrinsic width in pixels
  height?: number                  // Intrinsic height in pixels
}
```

**Constraints:**

- `url` must be an absolute URL (no relative paths, no data URIs, no base64).
- `alt` should be descriptive (not empty, not "image").
- Detected via standard markdown image syntax `![alt](url)`.

### 3.11 VideoNode

An embedded video, audio, or PDF player.

```
EmbedProvider = 'youtube' | 'vimeo' | 'html5' | 'audio' | 'pdf' | 'iframe'
```

```
VideoNode extends BaseNode {
  type: 'video'
  provider: EmbedProvider          // Embed provider type
  url: string                      // Content URL
  title?: string                   // Optional video title
  caption?: string                 // Optional caption
  posterUrl?: string               // Thumbnail/preview image URL
  duration?: number                // Duration in seconds
}
```

**Constraints:**

- `url` must be an absolute URL.
- Detected via `@[provider](url)` syntax in markdown paragraphs.
- `provider` determines the embed rendering strategy (iframe, HTML5 video/audio, PDF viewer).

### 3.12 EquationNode

A KaTeX-rendered mathematical expression.

```
EquationNode extends BaseNode {
  type: 'equation'
  content: string                  // LaTeX equation content
  displayMode: boolean             // true for block ($$), false for inline ($)
}
```

**Constraints:**

- Inline equations must use single `$` delimiters.
- Block equations must use double `$$` delimiters on their own lines.
- `content` must be valid LaTeX within the KaTeX-supported subset.
- Parsed during HTML rendering by `renderMath()`; not directly produced by the markdown lexer.

### 3.13 BlockquoteNode

A standard blockquote with optional citation.

```
BlockquoteNode extends BaseNode {
  type: 'blockquote'
  html: string                     // HTML-rendered quoted content
  citation?: string                // Optional citation or attribution
}
```

**Constraint:** Blockquotes whose first line matches the GFM alert pattern `[!KIND]` are promoted to `CalloutNode` during parsing.

### 3.14 ReferenceNode

A collection of external reference links.

```
ReferenceItem {
  id: string                       // Reference identifier
  text: string                     // Display text
  url?: string                     // Optional URL
}
```

```
ReferenceNode extends BaseNode {
  type: 'reference'
  items: ReferenceItem[]           // Reference entries
}
```

**Constraint:** `items` must have at least one entry.

### 3.15 DefinitionNode

A glossary-style term-definition pair.

```
DefinitionNode extends BaseNode {
  type: 'definition'
  term: string                     // The term being defined
  definition: string               // The definition text
}
```

**Constraint:** Both `term` and `definition` must be non-empty.

### 3.16 ThematicBreakNode

A horizontal rule (thematic break).

```
ThematicBreakNode extends BaseNode {
  type: 'thematic_break'
}
```

**Constraint:** No additional fields. Rendered as a horizontal rule or section divider.

### 3.17 SemanticBlockNode

A typed semantic annotation block for domain-specific content.

```
SemanticBlockKind =
  | 'architecture' | 'performance' | 'security'
  | 'api' | 'example' | 'history'
  | 'future-work' | 'timeline' | 'definition'
```

```
SemanticBlockNode extends BaseNode {
  type: 'semantic'
  kind: SemanticBlockKind          // Semantic domain
  title?: string                   // Optional display title
  html: string                     // HTML-rendered content
}
```

**Constraint:** `kind` must be one of the 9 defined `SemanticBlockKind` values. Detected via `:::kind` fenced container syntax during parsing.

### 3.18 TerminalNode

A terminal session recording (prompt/input/output lines).

```
TerminalLine {
  prompt?: string                  // Shell prompt string (e.g., "$ ", "> ")
  input?: string                   // User input text
  output?: string                  // Command output text
}
```

```
TerminalNode extends BaseNode {
  type: 'terminal'
  lines: TerminalLine[]            // Sequential terminal lines
  sessionName?: string             // Optional session label
}
```

**Constraint:** Each `TerminalLine` must have at least one of `prompt`, `input`, or `output`.

### 3.19 FileTreeNode

A file system tree structure for illustrating project layout.

```
FileTreeEntry {
  name: string                     // Entry name
  type: 'file' | 'directory'      // Entry type
  children?: FileTreeEntry[]       // Child entries (directories only)
}
```

```
FileTreeNode extends BaseNode {
  type: 'file_tree'
  entries: FileTreeEntry[]         // Top-level entries
  rootLabel?: string               // Optional root directory label
}
```

**Constraint:** `entries` must have at least one entry. `type === 'directory'` entries must have a non-empty `children` array.

### 3.20 AccordionNode

A collapsible panel group.

```
AccordionPanel {
  title: string                    // Panel header text
  content: string                  // Panel body content (HTML)
}
```

```
AccordionNode extends BaseNode {
  type: 'accordion'
  panels: AccordionPanel[]         // Ordered panel list
}
```

**Constraint:** `panels` must have at least one entry.

### 3.21 ApiNode

An API endpoint reference block.

```
ApiEndpoint {
  method: 'GET' | 'POST' | 'PUT' | 'PATCH' | 'DELETE' | 'HEAD' | 'OPTIONS'
  path: string                     // URL path template
  description: string              // Endpoint description
  requestBody?: string             // Request body schema or example (HTML)
  responseBody?: string            // Response body schema or example (HTML)
}
```

```
ApiNode extends BaseNode {
  type: 'api'
  endpoints: ApiEndpoint[]         // Endpoint definitions
}
```

**Constraint:** `endpoints` must have at least one entry. `method` must be one of the 7 defined HTTP methods.

### 3.22 ASTNode (Discriminated Union)

The complete union type enumerating all permissible content nodes:

```
ASTNode =
  | HeadingNode
  | ParagraphNode
  | ListNode
  | CodeNode
  | DiagramNode
  | CalloutNode
  | TableNode
  | ImageNode
  | VideoNode
  | EquationNode
  | BlockquoteNode
  | ReferenceNode
  | DefinitionNode
  | ThematicBreakNode
  | SemanticBlockNode
  | TerminalNode
  | FileTreeNode
  | AccordionNode
  | ApiNode
```

Every consumer (renderer, validator, transformer, exporter) must handle all 19 node types exhaustively. The TypeScript compiler enforces this via the discriminated union.

## 4. Validation Contract

### 4.1 Validation Result

```
ValidationSeverity = 'error' | 'warning' | 'info'

ValidationEntry {
  nodeId?: string                  // Affected node ID (if applicable)
  rule: string                     // Rule identifier (kebab-case)
  message: string                  // Human-readable description
  severity: ValidationSeverity     // Error severity level
  position?: SourcePosition        // Source location (if available)
}

ValidationResult {
  valid: boolean                   // true if zero errors
  errors: ValidationEntry[]        // Error entries (must be fixed)
  warnings: ValidationEntry[]      // Warning entries (advisory)
}
```

### 4.2 Heading Hierarchy Rules

| Rule ID               | Severity | Description                                                                                    |
| --------------------- | -------- | ---------------------------------------------------------------------------------------------- |
| `heading-hierarchy`   | error    | Heading level may increase by at most 1 from the previous heading. H1 -> H3 is invalid.        |
| `first-heading`       | error    | The first heading in the document must be level 1.                                             |
| `duplicate-heading`   | warning  | Duplicate heading text at the same level within the document.                                  |
| `empty-section`       | warning  | A heading is immediately followed by another heading at the same or higher level (no content). |
| `heading-level-range` | error    | Heading level must be between 1 and 6 inclusive.                                               |

### 4.3 Node Structure Rules

| Rule ID                 | Severity | Description                                                         |
| ----------------------- | -------- | ------------------------------------------------------------------- |
| `diagram-content`       | error    | Diagram content must be at least 3 non-whitespace characters.       |
| `diagram-content-lines` | warning  | Diagram content should span at least 2 lines.                       |
| `table-structure`       | error    | Every row must have the same number of cells as column definitions. |
| `table-columns`         | error    | Table must have at least one column definition.                     |

### 4.4 Allowed Values Rules

| Rule ID         | Severity                 | Description                                                                               |
| --------------- | ------------------------ | ----------------------------------------------------------------------------------------- |
| `callout-kind`  | error (strict) / warning | Callout kind must be one of the 9 defined `CalloutKind` values.                           |
| `code-language` | error (strict) / warning | Code language identifier must be in the allowed set. Unknown identifiers yield a warning. |
| `diagram-kind`  | warning                  | Diagram kind must be one of the defined `DiagramKind` values.                             |

### 4.5 Content Quality Rules

| Rule ID               | Severity | Description                                            |
| --------------------- | -------- | ------------------------------------------------------ |
| `image-alt`           | warning  | Image nodes must have non-empty alt text.              |
| `metadata-title`      | warning  | Document title should not be empty.                    |
| `metadata-word-count` | info     | Warning if document has zero words.                    |
| `definition-empty`    | error    | Definition term and definition must both be non-empty. |
| `reference-empty`     | error    | Reference must have at least one item.                 |

### 4.6 Validation Options

```
ValidationOptions {
  strict: boolean                  // If true, warnings become errors (default: false)
  checkExternalRefs: boolean       // If true, validate external URLs are reachable (default: false)
  maxHeadingDepth: number          // Maximum allowed heading level (default: 6)
  allowedCallouts: CalloutKind[]   // Whitelist of valid callout kinds (default: all 9)
  allowedLanguages: CodeLanguage[] // Whitelist of valid code languages (default: all 32)
  allowedDiagramKinds: DiagramKind[]  // Whitelist of valid diagram kinds (default: all 15)
}
```

### 4.7 Validation Rules

1. The validator runs all rules in sequence. Rule execution is independent (no rule depends on another rule's output).
2. Errors are collected and returned in aggregate.
3. A document is considered valid (`valid: true`) iff the `errors` array is empty.
4. Warnings do not affect validity but are surfaced to the user and to downstream quality scoring.
5. The `strict` mode elevates all warnings to errors, enforcing absolute compliance.

## 5. Serialization

### 5.1 JSON Format

The NDL AST serializes to JSON with the following conventions:

- The top-level structure is the `DocumentAST` object.
- Node `type` fields are serialized as string discriminants.
- Optional fields are omitted from serialization when `undefined`.
- `Record<string, unknown>` meta fields are serialized as JSON objects.

### 5.2 Complete JSON Schema

```json
{
  "title": "string",
  "metadata": {
    "sourceUrl": "string (optional)",
    "sourceDomain": "string (optional)",
    "wordCount": "number",
    "readingTimeMinutes": "number",
    "documentClass": "string (optional)",
    "capturedAt": "string (optional, ISO-8601)",
    "tags": ["string (optional)"],
    "complexity": "number (optional, 1-10)",
    "qualityScore": "number (optional, 1-10)"
  },
  "nodes": [
    {
      "type": "heading",
      "id": "string (optional)",
      "position": {
        "startLine": "number",
        "endLine": "number",
        "startCol": "number (optional)",
        "endCol": "number (optional)"
      },
      "meta": "object (optional)",
      "level": "number (1-6)",
      "text": "string",
      "number": "string (optional)",
      "children": ["HeadingNode... (optional)"]
    }
  ],
  "hierarchy": {
    "toc": ["HeadingNode..."],
    "figures": ["NumberedItem..."],
    "tables": ["NumberedItem..."],
    "diagrams": ["NumberedItem..."],
    "codeBlocks": ["NumberedItem..."]
  },
  "warnings": ["string..."]
}
```

### 5.3 Node Serialization Patterns

Each node serializes as a JSON object with the form:

```json
{ "type": "<discriminant>", ...fields }
```

The `type` field is always first and is required. All node-specific fields follow:

```
heading:     { "type": "heading", "level": 2, "text": "Architecture", "number": "1.2", "children": [...] }
paragraph:   { "type": "paragraph", "html": "<p>...</p>", "raw": "..." }
list:        { "type": "list", "ordered": false, "items": [{"content": "...", "checked": true}] }
code:        { "type": "code", "language": "typescript", "content": "...", "showLineNumbers": true }
diagram:     { "type": "diagram", "engine": "mermaid", "kind": "flowchart", "content": "..." }
callout:     { "type": "callout", "kind": "warning", "title": "Deprecation", "html": "..." }
table:       { "type": "table", "columns": [{"header": "Name", "align": "left"}], "rows": [["value"]] }
image:       { "type": "image", "url": "https://...", "alt": "Description" }
video:       { "type": "video", "provider": "youtube", "url": "https://..." }
equation:    { "type": "equation", "content": "E=mc^2", "displayMode": false }
blockquote:  { "type": "blockquote", "html": "...", "citation": "..." }
reference:   { "type": "reference", "items": [{"id": "rfc7231", "text": "RFC 7231", "url": "..."}] }
definition:  { "type": "definition", "term": "AST", "definition": "Abstract Syntax Tree" }
thematic_break: { "type": "thematic_break" }
semantic:    { "type": "semantic", "kind": "architecture", "title": "System Design", "html": "..." }
terminal:    { "type": "terminal", "lines": [{"prompt": "$ ", "input": "npm run build"}] }
file_tree:   { "type": "file_tree", "entries": [{"name": "src", "type": "directory", "children": [...]}] }
accordion:   { "type": "accordion", "panels": [{"title": "Details", "content": "..."}] }
api:         { "type": "api", "endpoints": [{"method": "GET", "path": "/users", "description": "..."}] }
```

### 5.4 Deserialization Contract

1. The `type` field determines the target interface.
2. Unknown `type` values cause a deserialization error.
3. Extra fields are tolerated (preserved in `meta` if they match the namespaced pattern).
4. Missing required fields cause a deserialization error.
5. Optional fields default to `undefined`.

## 6. TypeScript Implementation Notes

### 6.1 Base Pattern

All node interfaces extend `BaseNode` and use the `type` field as a string literal discriminant:

```typescript
interface BaseNode {
  type: string;
  id?: string;
  position?: SourcePosition;
  meta?: Record<string, unknown>;
}

interface HeadingNode extends BaseNode {
  type: 'heading';
  level: 1 | 2 | 3 | 4 | 5 | 6;
  text: string;
  number?: string;
  children: HeadingNode[];
}
```

### 6.2 Discriminated Union Exhaustiveness

The `ASTNode` union type must be updated whenever a new node type is added:

```typescript
type ASTNode =
  | HeadingNode
  | ParagraphNode
  | ListNode
  | CodeNode
  | DiagramNode
  | CalloutNode
  | TableNode
  | ImageNode
  | VideoNode
  | EquationNode
  | BlockquoteNode
  | ReferenceNode
  | DefinitionNode
  | ThematicBreakNode
  | SemanticBlockNode
  | TerminalNode
  | FileTreeNode
  | AccordionNode
  | ApiNode;
```

Consumers use type narrowing via `switch` statements:

```typescript
function renderNode(node: ASTNode): ReactNode {
  switch (node.type) {
    case 'heading':
      return renderHeading(node);
    case 'paragraph':
      return renderParagraph(node);
    // ... exhaustive cases ...
    case 'api':
      return renderApi(node);
  }
}
```

A `never` check at the default case ensures compile-time exhaustiveness:

```typescript
function assertNever(x: never): never {
  throw new Error(`Unexpected node type: ${x}`);
}
```

### 6.3 Import Convention

Every node type, the union, and all auxiliary types are re-exported from a single barrel at `@/document-system/schemas`:

```typescript

  type ASTNode,
  type DocumentAST,
  type HeadingNode,
  type ParagraphNode,
  // ...
} from '@/document-system/schemas';
```

### 6.7 Adding a New Node Type (Checklist)

1. Define the interface extending `BaseNode` in `src/document-system/schemas/index.ts`.
2. Add the new type to the `ASTNode` union.
3. Add a parser branch in `src/document-system/parser/index.ts` (if parseable from markdown).
4. Add optional validation rules in `src/document-system/validator/index.ts`.
5. Add ID prefix to `ID_PREFIXES` in `src/document-system/transformers/index.ts`.
6. Add to `weights` map in `enrichDocumentMetadata` if the type contributes to complexity scoring.
7. Export the new type from `src/document-system/index.ts`.
